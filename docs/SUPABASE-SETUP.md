## 1. Create your free project

1. Open [Supabase Dashboard](https://supabase.com/dashboard), sign in, and create an organization on the **Free** plan.
2. Create **Browser to Notion**, choose a region near your users, and save its database password in your password manager.
3. Wait for provisioning. Copy the project reference from `https://supabase.com/dashboard/project/PROJECT_REF`.
4. Keep the Data API enabled with the `public` schema exposed, which is the default. Do not expose `bns_private`.

Free-plan usage limits and inactivity pausing apply. A paused project must be restored before sync resumes; Chrome retains pending work. Check [current Supabase pricing](https://supabase.com/pricing).

## 2. Fill in the publisher configuration

From this project folder in PowerShell:

```powershell
npm install
npm run setup:supabase
```

`.env.supabase.local` has already been created in the current workspace with a new encryption key and the current extension ID. Setup preserves the file on later runs and never prints secrets. Fill in its blank fields directly:

| Field | Value |
| --- | --- |
| SERVICE_PUBLIC_URL | Open your project in Supabase. Copy the reference after `/project/` in its dashboard address and use `https://PROJECT_REF.supabase.co/functions/v1/notion-sync`. This endpoint becomes available after function deployment. |
| PRIVACY_URL | The actual HTTPS address of your published policy page from step 3. Supabase does not generate this value; fill in publisher/contact details first, generate the page, then publish it. |
| NOTION_CLIENT_ID | The OAuth client ID in your Notion integration's **Configuration** tab. If reusing the working pilot integration, this value is already in `.env.local`. |
| NOTION_CLIENT_SECRET | The matching OAuth client secret from that same Notion integration. If reusing the pilot integration, copy the same-named field from `.env.local`; keep it private. |
| TOKEN_ENCRYPTION_KEY | Already generated by setup. Leave it unchanged; it does not come from Supabase. Back it up securely. |
| ALLOWED_EXTENSION_ID | Setup fills the current build's ID. Verify it on this extension's card at `chrome://extensions`. For store release, use the store-assigned identity described below. |
| PUBLISHER_NAME | Enter your own name or the business name that operates the extension. This appears on the privacy policy. |
| SUPPORT_EMAIL | Enter an existing email address you monitor for help and privacy requests. It does not need to be issued by Supabase. |

Keep secrets out of chat, Git, the extension UI, and `VITE_*` variables. Supabase injects its project URL and server keys inside hosted functions. This implementation supports the default modern secret key and the legacy service-role key; neither goes to Chrome. [Function environment variables](https://supabase.com/docs/guides/functions/secrets).

For store distribution, upload a draft package to obtain its assigned ID/public key. Put that public key in `extension.config.json.key` and match `ALLOWED_EXTENSION_ID` to the store ID. `localKey` preserves the local pilot's identity. Use a separate Chrome profile for hosted testing; replace the old hosted test extension and reconnect if its ID changes. [Chrome key instructions](https://developer.chrome.com/docs/extensions/reference/manifest/key).

## 5. Apply the database migration

This project pins Supabase CLI **3.2.0**. Its remote target syntax is explicit:

```powershell
npx supabase login
npx supabase link --project-ref PROJECT_REF
npx supabase db push --remote --dry-run
npx supabase db push --remote
```

Replace `PROJECT_REF`. Complete login/password prompts directly in your browser/terminal. The dry run should list `202611180001_bookmark_service.sql` before applying it. No local Docker stack is needed for this hosted workflow.

The migration creates namespaced private tables with Row Level Security, no client grants/policies, and a service-only RPC. It handles one-time OAuth claims, hashed sessions, persisted authorization limits, refresh coordination, save locks, and uncertain writes. Anonymous and signed-in Supabase clients cannot read credentials or call the RPC.

Run the maintenance SQL against the linked project, or use the project's SQL Editor as its owner:

```powershell
npx supabase db query --remote --file supabase/maintenance.sql
npx supabase db query --remote --read-only --file supabase/verify-deployment.sql
```

This enables `pg_cron` and schedules hourly removal of expired flows/locks/rate-limit records and connections inactive for 90 days. The read-only verification should report five private tables with row security enabled, no anonymous/signed-in table or RPC access, service RPC access enabled, and an active `bns-hourly-cleanup` job scheduled at `13 * * * *`. Check the job in the Cron dashboard. This maintenance is for expiry, not a workaround for project pausing. [Supabase Cron installation](https://supabase.com/docs/guides/cron/install).

`verify_jwt = false` is intentional: Notion callbacks and the extension's PKCE/session protocol do not contain Supabase Auth JWTs. The handler checks OAuth state/verifiers, authenticates every private endpoint with its own hashed sessions, and requires the configured extension origin for API calls. Application logs omit environment values, OAuth codes, tokens, and bookmark bodies.

## Future migration and backups

The SQL and the `Repository` boundary separate persistence from HTTP and Notion logic. Export PostgreSQL tables and preserve the encryption key together when moving providers, or require users to reconnect. AES-256-GCM ciphertext uses the same IV/tag/data layout as the pilot. Users' Notion entries do not depend on Supabase Auth.

Do not change the encryption key without re-encrypting stored tokens or planning reconnection. Arrange deliberate exports before production if you need operator-managed backups, and update the policy with their retention. Preserve the current local pilot separately.
